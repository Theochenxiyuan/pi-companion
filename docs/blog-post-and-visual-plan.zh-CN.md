# 智能体不该住在聊天窗口里

Pi Companion 是我给自己做的一个 Pi 桌面 GUI。

在做这个 GUI 的过程中，我想验证两个关于智能体体验的想法，所以在里面加入了**快捷任务入口**和**任务监视器**：

1. 智能体任务能不能从工作发生的位置直接开始，而不是先打开一个聊天窗口？
2. 当智能体需要工作几分钟甚至更久时，能不能让它留在后台，只在真正需要我时让我介入？

我平时使用智能体处理的任务通常已经有明确上下文：一个目录、一个仓库、几份刚刚选中的文件。任务开始以后，我也不想一直守着对话记录。我只需要知道它是否还在正常工作、是否遇到了阻塞，以及最后做成了什么。

快捷任务入口和任务监视器，成了我在这个自用 GUI 里进行的一次产品实验。智能体对话仍然承担深入查看和连续工作的部分；我想知道的是，在它之外增加两个更轻的交互层级，会不会更适合真实任务。

> 在工作发生的地方启动智能体，让它在后台工作，只在需要你时出现。

【配图 1：首图——快捷任务入口、任务监视器、智能体对话三段式组合】

## 为什么要把“启动”和“监视”单独拿出来

聊天窗口非常适合澄清需求、连续讨论和查看详细过程。但当智能体从“回答问题”变成“执行任务”，交互条件也随之改变。

一个真实的编程任务可能会持续几分钟甚至更久。智能体需要读取文件、搜索代码、修改内容、执行命令、等待测试，然后在某个时刻请求权限或提出问题。在这段时间里，我往往还要浏览文档、查看其他代码，或者继续处理另一件事。

如果聊天窗口是唯一界面，我就需要：

- 一直保留一个占据大量空间的窗口；
- 不时切回去确认智能体是否还在工作；
- 在若干工具调用中寻找真正需要自己处理的内容；
- 担心错过权限请求、问题或失败状态。

这并不是聊天界面本身有什么问题，而是“启动任务”“监督运行”和“深入检查”对界面、信息密度与注意力的要求并不相同。把它们全部放在聊天窗口里，意味着我必须用最重的界面完成最轻的确认。

我没有把这个想法只做成概念图，而是直接放进自己日常使用的 Pi Companion 里，验证这种拆分是否真的更好用。

## 快捷任务入口：从任务的上下文开始，而不是从空白输入框开始

在桌面上，任务通常不是从一句孤立的话开始的。它往往已经有一个位置：某个目录、一个仓库、几份刚刚选中的文件。

所以 Pi Companion 的第一个核心入口不在智能体对话首页，而在 Windows 资源管理器。

我可以对当前目录、一个文件或一组选中文件点击 `询问 Pi Companion`。名为“快捷任务入口”的轻量窗口会出现在鼠标附近，并自动带入工作目录和附件。我描述任务、选择模型与权限，然后提交。

【配图 2：资源管理器选择文件 → 询问 Pi Companion → 快捷任务入口】

这个入口看似只是少打开一个窗口，但它改变了任务的起点：

- 我不必先创建“项目”或导入仓库；
- 目录本身就是智能体的工作上下文和默认边界；
- 已经选中的文件直接成为任务附件；
- 输入结束后，快捷任务入口可以立即离开，不需要继续占据屏幕。

它更像系统里的打印、分享或打开方式，而不是另一个需要先进入的应用。

## 任务监视器：保持可见，但不持续索取注意力

任务提交以后，我最关心的不再是“智能体刚才说了什么”，而是：

- 它现在处于什么状态？
- 它是否需要我？
- 如果完成了，结果是什么？

Pi Companion 用一个常驻桌面的任务监视器回答这些问题。

收起时，它只保留任务标题和状态；展开后，它显示精简的活动、当前交互和最终结果。它不会因为普通状态更新抢走窗口焦点，也不会把每一条底层事件都变成需要阅读的新消息。

【配图 3：任务监视器的运行状态与精简活动流】

我为任务监视器设定了三条原则。

### 1. 状态变化不等于打断

智能体读取文件、搜索代码、运行工具时，任务监视器可以更新文字、颜色或动画，但不能主动激活窗口。可见性应该让人安心，而不是制造新的通知流。

### 2. 需要人时，交互取代进度

当智能体请求权限或提出问题时，任务监视器的主要内容会切换成可直接处理的交互。我可以允许一次、拒绝、回答问题，或者立即调整智能体的方向。

【配图 4：任务监视器中的权限请求或智能体提问】

这类交互不应该埋在不断增长的消息记录里。此时最重要的内容不是“智能体刚刚做过什么”，而是“它现在需要我做什么”。

### 3. 完成意味着可以快速离开

任务结束后，任务监视器显示简洁摘要、文件变更、测试状态和警告。我能够在几秒钟内决定：接受结果、继续一轮任务，还是打开完整的智能体对话检查细节。

【配图 5：任务监视器的完成摘要、文件变更与测试状态】

任务监视器不是一个缩小的聊天窗口。它是任务状态的投影，也是高频人工介入的入口。

## 智能体对话负责深入查看

把快捷任务入口和任务监视器独立出来，并不意味着聊天不重要。

智能体对话仍然适合：

- 查看完整消息和推理过程；
- 审查工具调用、命令、文件差异和测试证据；
- 搜索历史任务；
- 进行需要上下文的连续对话；
- 在任务完成后继续下一轮工作。

区别在于，我不需要为了知道“任务是否还在运行”而打开它。

【配图 6：从任务监视器进入包含完整证据的智能体对话】

这形成了一个更明确的交互层级：

> **快捷任务入口负责开始，任务监视器负责陪伴和介入，智能体对话负责深入检查。**

快捷任务入口是短暂的，任务监视器是环境式的，智能体对话是按需打开的。三者共享同一套任务、运行与事件状态，但承担不同的注意力成本。

## 在自用的 Pi 桌面 GUI 里做实验

Pi 的价值之一，是简单和可定制。不同的人可以用扩展、技能和提示把它变成完全不同的智能体。

Pi Companion 本来就是我自己的 Pi 桌面 GUI，因此有非常明确的个人偏好：Windows、资源管理器入口，以及我自己的任务处理方式。它首先要解决的是我的问题，而不是覆盖所有 Pi 用户的工作流。

也正因为它是我真正使用的 GUI，我才能把两个产品假设放进真实任务里验证，而不只是制作一段理想状态下的演示：

- 从工作上下文直接启动任务，是否真的比先进入聊天窗口自然？
- 一个不抢焦点、只在必要时要求介入的任务监视器，是否真的能降低长任务的注意力成本？

为了在现有 GUI 中实现这两个功能，我选择 Windows 资源管理器作为任务入口，选择桌面悬浮窗口作为任务监视器，并继续使用 Pi RPC 作为智能体后端。这些是 Pi Companion 的具体方案，不代表其他实现必须作出相同选择。

我把 Pi Companion 的代码开源，也让这两个功能不只是一组静态概念图：它们可以运行、可以修改，也可以被实际讨论和继续探索。

## 当前实现与开源状态

Pi Companion 当前已经实现：

- 从 Windows 11 资源管理器的当前目录或选中文件启动任务；
- 自动带入工作目录与附件的快捷任务入口；
- 支持多个任务状态的桌面任务监视器；
- 在任务监视器中处理权限、智能体提问和方向调整；
- 任务完成摘要、文件变更与测试状态；
- 用于查看完整过程和继续对话的智能体对话；
- 基于本地事件存储的任务恢复，以及 Pi RPC 运行链路。

项目已经以 MIT License 开源，但仍处于早期开发阶段。目前没有经过代码签名的公开安装包，也没有稳定版本兼容承诺；需要在 Windows 11 上从源码构建，并自行配置 Pi Runtime 与模型服务。

【配图 7：GitHub 仓库与构建入口】

如果你也在思考智能体是否一定要以聊天窗口为中心，欢迎查看 Pi Companion 的代码、产品文档和实现方式。对我来说，这两个功能最值得验证的，仍然是最初的问题：从当前上下文启动是否更自然，以及任务监视器能否让人与长时间运行的智能体相处得更轻松。
